### METHOD-001 — P1, высокая: frontier proxy выдаётся как вероятность настоящего terminal

**Доказательство:** main `3e3f6e49da69b458a80fd9a0965852b6f0c87cb8`, `frontier.add_frontier_probability` обучает метку `out_deg==0` на depth 1–3, делает random CV и переносит на depth=4; `roles.assign_base_roles` использует p>=0.5 для role=terminal, score=p. Но целевой факт удержания денег неизвестен, CV измеряет proxy на другой глубине, а README не раскрывает это различие.

**Основание:** ограничения ТЗ §6 и собственная методическая рекомендация. Модель и отличие от пакета сами по себе не запрещены. **Ответственный:** kuznargi. **Исправление:** документировать proxy, переносимость, неопределённость и смысл score; отделить экспериментальную оценку от установленной роли. ### METHOD-002 — P1, высокая: temporal и seed-flow требуют явного модельного смысла

**Доказательство:** main `3e3f6e49da69b458a80fd9a0965852b6f0c87cb8`, `temporal._fast_pass`: подходящая исходящая может равняться 50% входящей, но в matched засчитывается весь входящий объём; разрешён тот же день. Для входа 100000 и выхода 50000 в тот же день формула возвращает share=1 и lag=0. Это допустимо как доля входов с совместимой парой, но не доля фактически прошедших денег. `flow.add_seed_flow` фиксирует share(seed)=1 и не экспортирует convergence/residual; `scoring.py` использует flow с весом 0.25 и temporal с 0.10. Структурные cycles не проверяют хронологию одной суммы.

**Основание:** данные date-only/нет начального баланса, explainability; рекомендуемое уточнение метода, не запрет optional. **Ответственный:** kuznargi. **Исправление:** либо назвать matched-показатель именно совместимостью пар с неопределённым порядком дня, либо учитывать реально выделяемый объём; описать mixing и сходимость. Не называть циклы доказанным возвратом тех же денег. **Приёмка:** пример 100k/50k не утверждает 100% денежный транзит; same-day оговорка видна; вклад модели в priority объяснён и проверен. **Стоимость:** 30–60 минут; до этого не усиливать заявления на демо.

## 11. Как Codex участника применяет этот файл

Пользователь передал этот отчёт для исправления своей части проекта. Сначала установи свою ветку и область владения; если соответствие неоднозначно, уточни его. Сверь текущий commit с проверенным SHA: для каждого ID повторно проверь, сохраняется ли проблема. Не откатывай более свежие удачные изменения.

Выполняй только подтверждённые и применимые к своей части исправления: P0, затем обоснованные P1. Если рекомендация неверна или уже есть лучшее решение, сохрани его и приведи воспроизводимое доказательство. Обязательное требование ТЗ нельзя отклонить как предпочтение. Для VERIFY сначала получи доказательства. P2 — только при готовом core, наличии времени и до freeze. KEEP не переписывай.

Не меняй чужие файлы и общий контракт самостоятельно. При необходимом совместном изменении подготовь конкретное предложение с ID и владельцами; продолжай независимые исправления. Не переименовывай публичные поля и не дублируй формулы.

На каждый ID сообщи `FIXED / ALREADY_FIXED / KEPT_WITH_EVIDENCE / DEFERRED / BLOCKED`, команду/пример, результат и изменённые файлы. Сохрани отчёт участника отдельно; не редактируйте общий файл одновременно. Фраза «всё работает» не заменяет доказательства.

К checkpoint зафиксируй только свою относящуюся к задаче работу. Commit/push выполняй в рамках отдельного поручения пользователя, обычным push в свою ветку; не включай чужие изменения, ключи, окружения и случайные файлы. Передай интегратору ветку, полный SHA, базовый SHA, проверки и нерешённые ID. Общую ветку объединяет назначенный интегратор. Зелёная проверка одной ветки не заменяет проверку общей версии.
